# TASK-010 — Sprint 2 AI Policy and Budget UI Remediation

## Objective

Give workspace owners a complete, safe UI for viewing and updating AI enablement, monthly budget, and request-rate policy so a newly created workspace can run the Sprint 2 analysis loop without manual database changes.

## Context

TASK-009 implemented durable AI policy enforcement and an owner-only update endpoint. New workspaces intentionally start with a zero monthly budget, but the web application exposes no policy controls. The existing web update client also omits the required optimistic-concurrency precondition. This leaves the primary analysis flow blocked for normal users.

## Required implementation

- Add an authenticated owner-only `GET /api/v1/workspaces/{workspaceId}/ai-policy` endpoint.
- Return the existing safe policy DTO and an `ETag` derived from its version.
- Preserve the existing owner-only `PUT` endpoint and require `If-Match` optimistic concurrency.
- Add a web client for reading the policy and correct the update client to send `If-Match`.
- Add an owner-only AI Policy panel that loads per selected workspace and exposes:
  - AI enabled/disabled.
  - Monthly budget in microunits.
  - Rate limit per minute.
  - Current spend, reserved spend, remaining budget, period start, and policy version.
- Provide bounded integer validation, accessible loading/error/success states, retry, and disabled controls while saving.
- Refresh the displayed policy from the server response after a successful update.

## Database changes

None. Reuse `workspace_ai_policies` and the existing atomic audited update transaction.

## API changes

- Add owner-only `GET /api/v1/workspaces/{workspaceId}/ai-policy`.
- The GET response uses the existing `WorkspaceAIPolicyDTO` schema and returns `ETag: "{version}"`.
- PUT continues using the same payload and response contract, with `If-Match` sent by the web client.

## Frontend changes

- Render policy controls only for workspace owners.
- Reset and reload state when the selected workspace changes.
- Display microunit values explicitly; do not imply a currency not defined by the domain contract.
- Do not expose provider credentials, prompts, or raw provider responses.

## Backend changes

- Authorize reads with active membership and `workspace.manage` capability.
- Use `WorkspaceAIPolicyPort.getPolicy`; do not access PostgreSQL from the route.
- Preserve no-store response headers and safe problem responses.

## Security requirements

- Authentication required.
- Only active workspace owners with `workspace.manage` may read or update policy.
- Tenant-scoped IDs must be parsed and authorized before policy access.
- No secrets in API responses, UI, logs, tests, or Git.
- Updates remain versioned and atomically audited through the existing adapter.

## Edge cases

- Zero budget is valid and must be displayed clearly.
- Budget and spend values must be non-negative safe integers.
- Rate limit must be an integer from 1 through 1000.
- Remaining budget must never display below zero.
- Workspace switches and aborted requests must not leak stale state.
- Stale versions must surface a conflict and allow reloading current policy.
- Missing adapter or unauthorized membership must fail safely.

## Acceptance criteria

- An owner can load and update policy entirely through the UI.
- Editors and viewers do not see the panel and cannot access the endpoint.
- A zero-budget workspace can be assigned a positive budget without direct database access.
- PUT sends the current version in `If-Match` and the next rendered version comes from the response.
- API route tests, web component/client tests, OpenAPI verification, typecheck, lint, unit tests, integration tests, and production build pass.

## Test plan

- API tests: owner GET success/ETag, editor GET denial, PUT success, PUT stale/authorization behavior.
- Web client tests: GET parsing, PUT headers/body, failure propagation.
- Component tests: loading, owner form, metrics, validation, and successful save state.
- Run `pnpm check`.
- Run PostgreSQL integration suite and migration validation.
- Browser-smoke the live owner workflow against local PostgreSQL.

## Out of scope

- Billing, payment methods, currency conversion, or automatic recharge.
- Chat-based creative planning, content briefs, video direction, or Sprint 3 content workflow.
